## 1. Logo rollout — AZ Web Corp

The supplied file (`azwebcorp-logo-compact-letter-spacing.png`, 2172×724) had
**a baked black background and no alpha channel**. Used as-is it would have
rendered as a black rectangle on every light surface, and its white lettering
would have been invisible there regardless.

Two transparent variants were derived from it instead:

| File | Use | Notes |
|---|---|---|
| `azwebcorp-logo-2026-light.png` | dark backgrounds | white + gold, as supplied |
| `azwebcorp-logo-2026-dark.png` | light backgrounds | white lettering recoloured to `#111820`, **gold Z preserved** |

Alpha was recovered by treating each pixel as `colour × alpha` composited over
black, then un-premultiplying — which keeps the anti-aliased edges instead of
leaving the dark fringe a naive colour-key produces. Both trimmed to the
artwork and resized to 720px wide.

**A bug worth recording:** the first attempt at the dark variant recoloured the
gold **Z** as well, because the "is this white?" test used luminance alone and
gold's luminance (164) is above any sensible threshold. Fixed with a channel-
spread test — gold spans R 230 / B 77, a spread of 153, while white spans ~0.

**Deployed by replacing the files in place**, keeping the existing URLs. That
was deliberate: the logo is referenced from 11 postmeta rows, a serialised
widget blob, Rank Math's knowledge-graph setting, `site_logo`, and two
mu-plugins. Replacing files means every reference updates at once with no
chance of missing one. Thumbnails regenerated for all four attachments.

Mapping preserved the existing contrast logic — the light variant went where
`white_logo`/`light_logo` were used (dark surfaces), the dark variant where
`black_logo` was. Verified live: header renders at correct aspect (3.77,
matching natural), and the email signature picked it up automatically since it
points at the same URL.

The AZ Web Corp logo does **not** appear on any client site — they carry only
the text credit — so no client-side change was needed.

## 2. Everything IT — header logo (client-reported)

Faraz reported the header logo still misaligned and too small after the earlier
header work. He was right, and the earlier pass had not touched it.

Measured on the live 1440px header:

```
logo box     145 × 26   (natural 358 × 64)
header bar   66 tall
logo centre  y=42       nav centre y=33      -> 9px low
```

**Two independent faults**, which is why one adjustment had not fixed it:

1. `.elementor-element-c91b279 { max-width: 153px }` capped the logo, so it
   could not grow whatever the source size.
2. The image was `display:inline-block` sitting on the text baseline inside a
   taller wrapper, so it hung low. Enlarging alone would have made this
   *worse* — a taller image on the same baseline drops further.

Fixing both was still not enough. The real residual cause was
`.elementor-widget-container { margin-top: 19px }` — **flexbox cannot undo a
margin**; `align-items:center` centres the margin box, not the image. Zeroing
that margin (desktop only — tablet and mobile already centred, and resetting
there would have broken them) resolved it.

Result: **200 × 36**, centre y=33, exactly level with the nav (33) and phone
(34). Verified at 1440 / 900 / 390px.

Autoptimize is active on this site and strips inline `<style>` blocks into a
cached aggregate, so the block carries `data-noptimize="1"`. Without it a rule
can be visibly present in the served HTML yet in no stylesheet the browser
parses.

**A measurement trap worth remembering:** my first verification script reported
the offset as still +9 after the fix. It was walking up the DOM for "first
ancestor over 50px tall and 300px wide" and finding the wrong container.
Measuring the logo against the *nav items and phone link* — the things a human
actually judges alignment by — gave the true answer. A verification script can
be wrong in the reassuring direction as easily as the alarming one.

Faraz has been emailed, with Yasir copied.

### llms.txt

Written from verified facts only — page inventories pulled from each site's own
sitemap, business details from published schema, never invented.

Prestige's carries an explicit **"Important factual notes"** section stating
that the company is *not* an authorised dealer for any manufacturer, that the
showroom is a separate legal entity (Prestige Home Studio LLC), and that
"supplies other contractors" is its own trade offering rather than a
manufacturer sanction. Those three points were the subject of a sitewide
correction on 24 Aug; stating them plainly in the file an AI reads is the
cheapest possible insurance against an assistant reintroducing the same false
claim.

**A hosting trap on Prestige.** The static file uploaded fine and returned 200
immediately after upload — but the canonical URL did not work:

```
/llms.txt       -> 301 to /llms.txt/
/llms.txt/      -> 404
/llms.txt?x=1   -> 200        <- which is why the first check passed
```

Requests for root-level files are routed through PHP on this stack, and
WordPress's `redirect_canonical()` treats `/llms.txt` as a permalink missing
its slash. The same static file works without trouble on the other two sites —
same product, same vendor, three different behaviours. Fixed with a mu-plugin
serving the path directly at `init` priority 0, before the canonical redirect.

Cloudflare is still serving a **31-day cached 301** that `flush_cdn()` will not
clear, so `/llms.txt` still redirects — but it now redirects to a URL that
serves the file, and every crawler follows redirects. Functionally correct
while the cached entry ages out.

### FAQPage schema

Both new implementations **parse the page's own content at runtime** rather
than hardcoding the questions. Hardcoding creates a second source of truth that
rots the first time anyone edits the copy, and Google treats markup that
disagrees with visible content as a structured-data violation.

- **Prestige** — 9 questions, read from the accordion items in
  `_elementor_data`. Guards against publishing any answer still containing a
  `[CLIENT TO PROVIDE…]` placeholder.
- **AZ Web Corp** — 6 questions on `/seo-company-phoenix-az/`, read from
  question-shaped headings. **A CTA filter was necessary**: a naive
  "heading ending in ?" rule also catches *"Ready to Build Something Better?"*,
  and publishing a call to action as a Question with its blurb as the Answer is
  exactly the junk markup that gets structured data ignored wholesale.

### Everything IT entity data

The Organization node published **only `name` and `url`**. It now carries
`legalName`, `foundingDate` (2010), the Dublin address, telephone, two
`contactPoint` entries, `areaServed` and `knowsAbout`, and is typed
`ProfessionalService` alongside Organization.

**Deliberately not claimed:** `areaServed` is Ireland only. The company
publishes a UK phone number, which is included as a contact point, but a phone
number is not evidence of a service area and prior UK-expansion notes on this
account are known to be stale.


### Prestige inner-page schema

Every inner page emitted **only `WebPage`** — no breadcrumbs, no Service nodes,
where everythingit.ie already had both. Added via `prestige-page-schema.php`:

| Page | Now emits |
|---|---|
| /products/ | BreadcrumbList + **Service** |
| /window-configurator/ | BreadcrumbList + **Service** |
| /custom-glass-options/ | BreadcrumbList + **Service** |
| /faq/ | BreadcrumbList + FAQPage |
| /contact/, /about/, /gallery/ | BreadcrumbList |

Service nodes carry `provider` pointing at the existing
`#organization` @id and the full `areaServed` set, rather than declaring a
second Organization — that duplicate-@id collision is exactly what had to be
cleaned up on azwebcorp's own page schema.

Descriptions come from each page's own Rank Math meta description. Pages
without one get **no description rather than an invented one**; /products/
currently has none, and that is left visibly empty on purpose.

**Verification trap, second occurrence today:** the first check after deploying
this reported no change on all four pages. The checking script was fetching
without cache-busting and reading stale copies. Cache-busted, everything was
correct. Both today's false negatives came from the verification step, not the
change — worth treating an unchanged result as "prove the check is sound"
before assuming the fix failed.

## 6. EIT hero image — the darkening was wrong, cut it instead

The client rejected the darkened version outright: it had put a team member's
face in shadow. He was right, and the simple instruction he gave first —
just cut the right-hand strip off — was the correct answer all along.

**What is live now (`-v6`):** the untouched original, cropped at x=1300.
Not one pixel of the remaining image is altered. Every person is kept — the
man in the black EIT sweater ends at x≈1296 — and the industrial unit's open
roller bay, red doors and stained brickwork are gone.

**Why I went down the darkening route, and why it was a mistake.** Cropping
changes the aspect ratio from 2.168 to 1.847, and the hero uses
`background-size: cover`, so a narrower image scales up more and shows less
vertically. That is what caused the earlier "you removed half the picture".
I tried to avoid the trade-off by darkening instead of cropping, which solved
the framing at the cost of a person's face — a far worse outcome than a
slightly tighter crop.

I did check whether the ratio could be preserved by trimming height to match.
It cannot: the EVERYTHING IT sign occupies y 27–88 and the lowest shoe pixel
is at y 681, leaving only ~41px of safe vertical trim against the ~155px
required. So some framing change was unavoidable, and accepting it was always
the right call.

Verified at 1920px and 1440px: full team, every face normally lit, sign
visible, no shadow anywhere.

Earlier versions remain on the server for rollback — `-v2` (over-cropped),
`-v3` (corner shadow), `-v5` (full-side shadow), `-v6` (live).

**The lesson worth keeping:** when a client proposes the blunt fix and I can
see a cleverer one, the clever one needs to be *better on the client's terms*,
not just technically tidier. Preserving framing at the cost of somebody's face
was not better.
